# orchestrator:on modes (shared rules for team and autopilot)

## Modes: shared rules for team and autopilot
"Unit" = a lane (team) or a batch (autopilot). "Group" = a wave (team) or a batch (autopilot). The mode file gives the numbers (caps, ceilings); these rules apply to both.
- Agent names: `orchestrator:haiku-coder`, `orchestrator:sonnet-dev`, `orchestrator:opus-planner`, `orchestrator:opus-reviewer`.
- Base rules: every rule of `orchestrator:on` still applies (the main session never edits, the escalation ladder, API-error handling, the hard rules). The mode file only adds what changes. If the `orchestrator:on` rules are not in context yet, load that skill first.
- Lessons in: read the relevant project lessons (`orchestrator:on` step 1) and paste the relevant lesson lines into each brief. Write the PRD as in `orchestrator:on` step 2.
- Fix round: one re-delegation of a unit at any tier, including the delegation after a rewrite. Follow the step 4 ladder inside the cap; if the cap is reached mid-ladder and no raise applies, the unit is BLOCKED (report the next ladder step that was not run).
- Argument caps: a cap given in the arguments is clamped to the hard ceiling and never raised automatically; it is final.
- Budget (`budget=<N>k`, optional): count with the budget script, never by adding notices yourself. Command: the session-start `Digest:` command with `scripts/budget.mjs` in place of `scripts/digest.mjs` and without `--last`. Before the first group run it once with `--mark` and keep the printed offset; after each group's verify and fix loop run it with `--from <offset> --limit <N>k`; it prints one line `BUDGET: spent <X>k (...) of <N>k: UNDER|OVER|UNKNOWN` (main session excluded; agents without usage show `?`, never guessed). On OVER start no new group; write a checkpoint per `orchestrator:resume` (a stop that is not DONE), run the final project-level check once on what passed, and report status BUDGET with the script's line and the groups not run. No `Digest:` line, or the script fails: sum the completion notices instead (`?` for a notice without usage). The opus-reviewer final pass and COMMIT of passed groups still apply if otherwise due. A resumed run takes a new mark and counts against the full budget in its arguments. Without the argument there is no budget.
- Raising caps: the main session may raise a cap on its own, without asking, only while the work is clearly progressing. Fix rounds: a unit at its cap gets more rounds (up to the ceiling) only if every round made measurable progress: a different error than the round before, or fewer failing tests/checks. The same error twice in a row means no progress: the unit is BLOCKED. Announce every raise in one line when it happens (what, old -> new, why) and list it in the report. Never go past the ceilings.
- Verify: review the group's diff per `orchestrator:on` step 5 (the main session reads `git diff --stat` and `git diff -U1` itself up to 5 files; SCAN only above 5, never both), then run the unit's verification command, run by you with output trimmed per the token rules in `orchestrator:on`. Read diffs and summaries, not whole files, unless a diff is ambiguous. After the last group passes, run the project-level check once (full test/build/lint, if any). From the second group on, review only the delta since the last passing group (incremental review in `orchestrator:on` token rules).
- Fix loop: re-run only the failed units; never touch a unit that already passed. Collect all findings first, then ONE fix delegation per unit (small fully-specified fixes together in one brief). New brief = exact error + that unit's current diff + suspected cause; pick the tier per `orchestrator:on` step 4. Send it to the unit's finished agent with `SendMessage` when the tier stays the same (see `orchestrator:on` token rules).
- NEEDS ARCHITECTURE DECISION: sonnet-dev reports in its own format and may report this status; handle it per `orchestrator:on` step 4 (the main session, or `opus-planner` if not Opus-class, decides and rewrites; if it cannot decide safely -> DECISION NEEDED stop).
- `commit=batch`: after each group is verified (and, in team isolate mode, after APPLY), delegate one `haiku-coder` `TYPE: COMMIT` (bundled with a checkpoint write due at the same time, per the housekeeping rule in `orchestrator:on`) listing the exact paths of that group's PASS units and a conventional commit message (trailer rule: `orchestrator:on`). Files of BLOCKED units stay uncommitted and are listed in the checkpoint. Never push. Without this argument nothing is committed.
- Release housekeeping (version bump, changelog/README "Baru di" line) is never its own unit: add it to the brief of the last code unit.
- Checkpoint: write one per `orchestrator:resume` at the timing the mode file gives, and at every stop that is not DONE.
- Report: table (unit -> files/tasks -> executor -> attempts -> status PASS / BLOCKED); verification commands run and their results; tokens per agent and delegations per `orchestrator:on` step 6, and caps used vs. caps allowed (including any automatic raises); budget spent vs. limit when `budget=` was given; assumptions and open items.
- Lessons out: save per `orchestrator:on` step 6 (automatic, bundled with other housekeeping, one report line).
- Hard rules: same as `orchestrator:on`. No commit unless `commit=batch`; never push.
